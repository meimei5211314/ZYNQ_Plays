先说清楚断电会破坏什么

持久化设计依赖介质契约：最小编程粒度、页边界、擦除块、1→0限制、最小原子写单位、写缓存与同步语义。文件write返回成功不一定等于已到非易失介质；Flash控制器busy清除也需按芯片手册理解。NOR、原始NAND、eMMC和SD卡的故障与管理层不同，不能把一个字节数组模型的结论直接宣传为所有介质都抗断电。

Python模型假设两槽独立、单字节赋值原子完成且允许任意0↔1改写；断电保留已写前缀，恢复重新扫描。这可验证提交顺序，却不模拟NOR擦除、电压跌落、FTL或设备缓存。实际工程还要规定欠压检测、最低写电压、保持时间与存储错误返回。先明确允许丢最后一次更新、必须保留上一次已确认值，还是要求每次确认都已持久化；不同需求决定何时才能向上层回成功。

双槽的核心是保留一份已确认旧值

用A、B两个独立槽存同一种配置。参考格式为generation:u32LE、length:u16LE、定长payload区、CRC32和commit:u8；未用载荷字节填FF，CRC覆盖代数、长度及整个定长区，commit=A5才可参与恢复。产品协议可扩展magic与格式版本，并把恢复关键字段纳入校验；这些字段不在当前Python格式内。未提交但CRC恰好正确的记录仍不可见。

真实NOR方案只擦写非活动独立块，写数据与CRC、验证、最后提交并确认持久化；Python则先使非活动槽commit失效，逐字节改写正文和CRC，最后写A5，不执行擦除。两者都保留活动旧槽。若两个NOR槽在同一擦除块，擦目标也会破坏旧值，逻辑“双槽”不等于物理独立。槽大小、对齐、提交编程单位和允许重复编程次数必须按器件核查，不能照搬允许任意位改写的模型。

最后提交也必须有物理实现前提

“先写数据，最后写一个valid=1”不是脱离介质的万能方案。以擦除后全1的NOR为例，可设计从全1到某个提交图样的1→0编程，但提交标志的撕裂写入如何识别、是否允许同页再次编程、周边数据是否受扰动都需有依据。若器件不保证所需提交单位和写入次序，必须借助更合适日志、文件系统或存储抽象，而非在C代码里增加volatile。

# 逻辑流程示意，不是Flash驱动代码
erase(inactive_slot)
program(header_without_commit, payload, crc)
wait_and_verify_media()
program_commit_marker()
wait_until_commit_is_durable()
acknowledge_success()

CRC主要发现数据损坏，不能强迫写入顺序，也不能证明未提交操作已经完成。有限CRC存在碰撞概率，不能把“通过CRC”叫作数学上绝不出错。提交标志表明记录可参与恢复；只有介质确认机制保证提交及其前置数据持久后，才能向要求持久性的上层确认。把这三个条件分别写进状态机。

序号、版本与恢复决策

参考模型代数从1开始，选最高有效代数；到0xFFFFFFFF后拒绝继续写入，不静默回绕。另一种方案可约定“有效记录间代差小于2³¹”，用模2³²差值d=(a−b)，当0<d<2³¹判a较新；恰为2³¹则有歧义。这是设计扩展，不是当前Python实现。相同代数却内容不同也应在产品中有诊断策略。

两个槽均有效时选更新记录，只有一个有效时选它，都无效时参考recover()返回None；产品应进入明确缺省或恢复模式并报告。扩展版本字段后应让旧软件拒绝未知格式或按约定降级，不能强转成旧结构体。默认值应安全且可追踪，不能把配置丢失静默当正常启动。多项配置一致更新应放在同一事务记录或采用完整事务机制；逐项双槽会留下跨项组合不一致，这不是单条记录CRC能够解决的问题。

用断电切点验证原子恢复

参考labs/reference/journal.py提供TwoSlotJournal.write(payload,cut_after=N)，表示完成前N次字节赋值后断电；export_slots与from_slots重建恢复器，recover返回(代数,载荷)或None。先写旧配置A，再更新到B，穷举write_operations范围的切点。可接受结果只能是完整旧配置或已合法提交的新配置，不能选混合值或未提交值。

# 仓库根目录运行实验包的断电切点等自检
python -m unittest discover -s labs/tests -v
python -m labs.reference.capstone

浏览器演示压缩为六个逻辑阶段，便于定位旧槽保留的作用；Python按字节切点检查，两者都不代替物理试验。额外核查CRC损坏、长度越界、两槽无效、提交截断、复用旧槽与代数上限。加入版本字段的产品扩展还需未知版本用例。先声明切点模型，再用实际器件电源切断试验覆盖模型外风险，不能把复位当作中断Flash供电。

可靠恢复不等于无限寿命

设每槽独立擦除块，额定耐久上限为10万次擦除，每次更新擦一个槽、两槽轮换。理想均匀条件下总共约20万次更新；每分钟更新一次，约138.9天。若每秒更新一次，只约2.31天。这只是擦除预算算例，不是任何芯片的寿命承诺；温度、保持时间、实际额定值、写放大和坏块都要另行分析。

低频配置可以合并连续修改、只在值变化时提交、设定最短保存间隔；但要明确这会增加允许丢失的最近更新窗口。高频运行日志更适合多块追加、循环磨损均衡或专用介质，而非反复擦两个块。预留备用块与故障计数，设计接近寿命或编程失败后的降级策略。文件系统或FTL的磨损均衡也不免除应用层提交与同步责任，应分别量化逻辑写入率和实际介质写放大。

从教学日志迁移到产品存储

littlefs公开设计利用元数据对、校验和写时复制等机制处理小型Flash上的恢复与磨损问题，可作为设计阅读案例；本课双槽配置器只是更小的教学协议，并不实现littlefs。若采用现成文件系统，应按其块设备接口配置read/program/erase/sync及几何参数，不能把Python字节数组替换成任意write回调就宣称完成移植。

最终验收包包括介质数据手册条件、槽的物理布局、提交确认定义、恢复优先规则、切点枚举、错误注入结果和擦除预算。实际电源试验记录切断时间、写入阶段、复位原因、恢复值和介质错误，避免只按一次复位按钮代替断电。对于启动镜像A/B更新，还需增加镜像认证、启动选择、试运行与回滚等状态；配置双槽的CRC与提交位不能单独保证启动镜像安全。沿着介质契约逐层补齐责任，才能把“重启后还在”变成可审计的持久化保证。

运行journal自检，使用cut_after、export_slots和from_slots检查字节切点；在浏览器六阶段模型验证旧槽保留条件。

故障练习：翻转新槽CRC或截断提交，再另建同擦除块故障模型，解释Python赋值模型未覆盖的真实NOR架构失败。
