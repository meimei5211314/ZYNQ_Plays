先写一份精确到字节的契约

课程实验帧为A5 5A | version=01的一字节 | payload_len的u16小端 | seq的u16小端 | payload | CRC16的低字节、高字节。payload_len只表示载荷，范围0–256，整帧长度9+L，最大265字节。CRC使用Modbus算法，但这份帧格式是课程自定义协议，不是Modbus RTU；不能把RTU的站号、功能码或静默间隔假设带进来。

偏移长度字段
02A5 5A
21version
32L，小端
52seq，小端
7Lpayload
7+L2CRC，小端

CRC覆盖version开始到payload结束，即[2,7+L)，不含magic与CRC字段。seq回绕为16位序号，重复/乱序处理属于上层业务，不由CRC决定。payload允许包含A5 5A，合法帧内不能见到magic就提前截断。版本、长度、序号、载荷语义应分层检查，避免一条损坏数据触发实际设备动作。

流式输入不承诺一读就是一帧

串口read、TCP接收和DMA分块都可能在任意字节处分段。一次输入可能只有A5，下一次从5A开始；也可能一次含三帧半。解析器需要持久化有限状态或有限缓冲区，先找magic，再等固定头，校验版本和长度，等到9+L字节后校验CRC，最后一次只交付完整有效帧。空输入应保持状态，不等于连接结束或丢弃半帧。

当没有找到完整magic时保留可能作为前缀的最后一个A5，其余噪声可丢弃。坏版本、超长头或坏CRC时，应按明确策略继续搜寻后续候选；常见保守方案从候选起点之后逐字节重扫，避免整块丢弃而漏掉紧随其后的合法帧。合法长度但永不补全的半帧还需上层超时或连接重置契约。受控最大帧长限制单个候选，持续流入的批量数据则需循环消费和整体缓冲上限，不能无界累积。

先检查剩余，再读取和分配

C实现先确认固定头已齐，再读取L，拒绝L>256，最后确认剩余字节足够。不要先访问p[4]才判断头是否存在，也不要先按声称长度分配内存。对于一般格式，检查offset+length≤size可能发生无符号加法回绕；应先证明offset≤size，再检查length≤size−offset。对于多项记录，先判断count≤SIZE_MAX/item_size再乘。

/* 长度检查片段；buf为字节数组，n为当前可用字节 */
if (n < 7u) return NEED_MORE;
size_t len = (size_t)buf[3] | ((size_t)buf[4] << 8);
if (len > 256u) return BAD_HEADER;
if (n - 7u < len + 2u) return NEED_MORE;
/* 到这里才可访问完整payload与CRC */

本协议len+2因上限已受控而安全；这不表示任何协议都可以直接相加。不要把字节地址强转为uint16_t*来解析小端字段，它可能未对齐且依赖主机字节序。错误返回值要区分“还需输入”和“确定无效”，否则上层可能把合法拆包当坏帧，或者永远等待一个已知非法的头。

CRC参数要有可复核测试向量

CRC16 Modbus初始化0xFFFF，每输入一字节先异或低8位，再逐位右移；移出的最低位为1时异或反射多项式0xA001，无最终异或。线上低字节先发。对ASCII字符串123456789，结果为0x4B37；这个测试向量用于检查算法参数，仍需另测本协议的覆盖范围和序列化。

# 本协议空payload、seq=0的完整帧（独立算例）
A5 5A 01 00 00 00 00 19 C0
# CRC覆盖：01 00 00 00 00，结果0xC019

把seq改为1时，即使payload未变也应重算CRC，因为序号在覆盖范围内。故意只计算payload可能让空payload的所有序号得到同一CRC，正常收发测试未必马上暴露。CRC用于检错，不提供身份认证或防恶意修改；攻击者可以改字段后重算CRC。若有安全控制命令，应由上层增加适合的认证、重放防护和权限约束，而非扩大CRC位数冒充认证。

用性质组织测试，而非只列几帧

第一条性质是编码后再解析得到相同的版本、序号与载荷；第二条是分块不变性：同一串字节一次喂入、逐字节喂入、任意切块喂入，输出有效帧序列一致。第三条是边界与资源：0/1/255/256字节载荷可处理，257被拒绝，所有截断前缀不交付半帧，连续噪声不导致无限缓冲。第四条是坏帧后的合法帧可恢复。

在有效语料中加入载荷含magic、序号65535→0、空帧、连续多帧，再按位翻转头和CRC、删除字节、插入噪声、拆开magic。变异测试未必每次都应输出零帧：随机变异可能偶然形成另一合法帧，因此检查器应验证输出本身合法及资源/终止性质。对精确设计的单比特CRC破坏用例，则可以断言原帧不被交付。随机试验固定种子，失败保存最小字节串与分块位置。

先跑参考实现，再做覆盖引导模糊测试

参考labs/reference/protocol.py中FrameParser.feed(chunk)返回(序号,bytes载荷)列表，保留缓冲上限265字节；半帧超时由传输层调用expire_partial()并处理返回帧，新半帧须有自己的超时。浏览器使用固定字节流，可调1–20字节块并注入噪声/CRC错误，不接收任意协议输入；任意切分、L=257与超时在Python中验证。Python自检也不等于已运行libFuzzer。

# Python 3，在仓库根目录运行
python -m unittest discover -s labs/tests -v
python -m labs.reference.capstone

C/C++移植版可再写LLVMFuzzerTestOneInput入口，单次输入只驱动有限解析状态并检查不变量，用Clang的-fsanitize=fuzzer,address,undefined构建受支持环境。需要重置每次输入的状态、限制内存与步数、保留能推进校验深处的有效种子。覆盖引导会寻找新路径，却不自动知道业务结果对错；往fuzz入口补上分块不变性和编解码一致性检查，才有机会发现不崩溃的逻辑缺陷。

解析成功之后仍要通过业务门

CRC正确只说明收到的字节满足本帧检错规则。上层还要核对命令类型、字段范围、状态机允许性、序号窗口与资源预算。更新采样率的合法帧也可能在DMA运行中不允许立即执行。应先解析成普通数据结构，再交给经过检查的业务层，不在解析半帧过程中修改硬件寄存器或提交不可逆动作。

错误统计至少区分噪声字节、坏版本、超长、CRC错、超时和业务拒绝，避免用一个“串口错误”计数掩盖问题。性能测试报告每秒输入字节、有效帧吞吐、峰值缓冲和坏帧比例，特别测大量magic前缀和合法长半帧造成的扫描开销。生产实现可采用有限状态机或有界环形缓冲减少移动与重扫，但优化后仍需保留相同性质。最终验收应有协议表、测试向量、恢复策略、资源上限和失败回归，而不是只显示一帧解析成功。
