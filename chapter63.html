机制、约束与验证

每条结论说明条件，每个实验保留可以复查的结果。

构建输入必须能重新取得

“代码在 Git 里”只覆盖部分输入。列出硬件导出文件、Vivado/Vitis/PetaLinux 版本、BSP、Yocto 层、补丁、内核配置、设备树、应用源码、工具链、下载镜像源、构建主机或容器摘要。每项写不可变版本、获取位置和校验值；分支名会移动，不能独自充当发布标识。密钥属于受控签名环境，不能为了重建方便打包进构建清单。

可追溯表示知道产物来自哪些输入；可重复表示同样流程能再次得到功能相当的产物；位级可复现要求指定条件下字节完全相同。前者不能代替后者。即使镜像哈希相等，也没有证明算法正确，只证明此次比较的内容一致。

课程基线为 2020.2，不能直接把新 Yocto 文档中的变量复制进旧工程。建立版本说明，把“旧工程实际支持”与“现代流水线参考能力”分列。现代 SBOM 类若在旧层缺失，应显式编写工具兼容或升级方案，禁止伪造一个未执行的生成步骤。

把产品变化放进自己的层

Yocto 的层是元数据边界：BSP 层描述机器，产品层决定软件集合，应用配方描述构建安装。不要直接修改上游层再靠一份口头说明保留差异。建立 meta-product，纳入 layer.conf、镜像配方、设备树补丁和配置片段，使用与冻结分支兼容的 .bbappend 语法。

bitbake-layers show-layers
bitbake-layers show-appends
bitbake -e core-image-minimal > image-environment.txt

命令在匹配版本的 Yocto 构建环境中执行。先用 show-layers 核对实际参与的层，再查追加配方是否被匹配，最后在环境输出中确认变量最终值。仅看到文件存在，不能证明它影响了镜像；层优先级和覆盖语法可能让配置悄悄失效。

举例：产品层要求日志占用上限，BSP 层却打开了调试服务，交付差异应记录到最终包清单，而不是只检查 local.conf。构建目录中的临时修改必须转为版本化输入。新增一行配置后，检查产物变化是否与预期一致，避免无意带入开发工具和凭据。

找到字节不相同的真正原因

构造两次干净构建，使用同一输入清单，在不同绝对路径或不同时间运行。先比较镜像摘要，再逐层比较分区、归档成员和 ELF。常见差异来自时间戳、绝对路径、随机标识、文件遍历顺序以及未固定的网络下载。缓存命中使第二次更快，但不能因此证明独立重建成功。

设发布含 4 个组件，两个 rootfs 哈希相同，而内核不同。应比较内核配置、构建标识与编译信息；不能把整包不同直接归因于源码改变。采用规范化时间来源和路径映射前，先证明它们确实解释了差异。忽略字段必须有理由，忽略后比较叫规范化比较，不叫原文件位级一致。

准备一份重建报告，记录机器环境、命令、输入摘要、开始结束时间、两次产物摘要和差异解释。下载源离线镜像与源码许可材料要一起保存；只保存 sstate 缓存无法替代源码和配方。断网构建是否通过是有价值的供应链探针，但需先定义允许的本地输入。

SBOM 与发布清单互相连接

SBOM 描述组件、版本、依赖、来源和许可等信息；发布清单把这些信息绑定到具体设备镜像、测试报告和硬件兼容标识。二者不是同一个文件。SBOM 没有自动证明漏洞不可利用，也没有把未列出的二进制变安全；应抽查一个关键库，从配方追到包，再追到 rootfs。

在支持 create-spdx 的现代 Yocto 版本中，可按对应版本文档启用该类；2020.2 工程先检查实际类和变量。旧项目可先导出包清单、源修订与许可清单，清楚标注距离目标 SPDX 输出还缺什么，不能把普通文件列表改后缀称为合格 SBOM。

示例发布 R17 包含镜像、配置、硬件导出与测试四类摘要。若重新打包只改变压缩时间，外层摘要改变也必须重新登记；若内容哈希改变，关联的测试证据需要确认是否仍适用。清单中保留构建输入 ID、产物 ID 和验证 ID 三条关联，让评审者无需猜测截图对应哪次编译。

CI 应有明确入口和失败门槛

流水线依次执行输入核验、构建、主机测试、静态检查、镜像检查、板级测试、产物归档与受控签名。每步把退出码传递给下一步，不能在测试失败后用“继续执行”生成绿色发布。板卡离线时标为未执行并阻止要求板测的正式发布，主机模型通过不能冒充板级通过。

python -m unittest discover -s labs/tests -v
python -m labs.reference.capstone

这两条是本仓库主机功能基线，执行目录为仓库根。保存解释器版本、提交号、标准输出与退出码；一次随机失败也应留下原始日志。大型 FPGA 构建还要记录种子和实现报告，即便流程确定，时序结论也必须绑定具体实现产物。

发布权限与普通构建权限分离，防止任意分支直接调用生产签名。归档采用不可变名称，附容量和保存策略。流水线模板只是流程描述，验收时应实际运行一次故意失败的测试，证明失败确实阻断后续发布，而不是只看配置文件。

把构建交给另一位工程师

交接实验要求同伴在新的构建目录按说明取得输入，完成最小镜像或主机实验，并找到任意一项产物的源码修订。计时的是实际步骤，不预设“十分钟完成”。所有人工选择都回填到说明中；“先找我拷一个文件”表示仍存在未登记依赖。

计算归档容量：若每版完整产物 1.5 GiB，每月 4 版保存一年，基线为 72 GiB；再计日志、源码镜像、冗余和增长率。该数字是容量规划示例，不是课程实测。对空间不足的处置应是明确保留策略，不能静默覆盖仍在现场使用的版本。

验收包至少含输入清单、执行命令、实际输出、差异报告、包清单或 SBOM、许可材料索引以及恢复说明。请另一人随机抽一个组件，沿发布清单追到仓库修订和测试。构建失败与“无法重建”分开记录：前者可能是代码错误，后者往往是输入、环境或访问依赖丢失。

工程任务 · 为课程主机实验及一个冻结 BSP 工程制作可重建发布包。

执行两次干净主机构建或测试，保存版本、命令、摘要与产物清单；Yocto 部分在匹配环境中执行。

故障练习：撤掉一项未登记依赖、移动分支和使一项测试故意失败，观察流水线是否阻断。

验收：另一人能够从输入清单复现流程；每个结论绑定产物；不把新 Yocto 类假定为 2020.2 自带。
