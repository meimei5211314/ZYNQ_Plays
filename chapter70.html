先写控制安全状态与时限

项目目标是让周期控制在规定时间内使用有效输入，并在输入过期、配置损坏或升级失败时执行明确动作。先定义采样周期、允许年龄、输出截止期、执行器限制和恢复条件。安全状态取决于设备：某装置是停止驱动，另一装置可能需要保持受限输出，不能用统一“输出清零”替代风险分析。

教学候选需求为控制周期 5 ms、响应截止期 2 ms，配置更新由后台任务处理，升级只在允许的维护模式进行。数字用于预算演练，不是任何工业设备的安全指标。主机模型没有真实被控对象，只能验证状态与时限假设，不能证明闭环稳定性或满足功能安全标准。

将系统画成运行、降级、维护、恢复四类状态，写出进入条件、允许动作与退出条件。收到一个看似正常的新输入不应立刻解除故障，还需考虑持续健康判据和人工确认需求。控制状态与升级状态分开建模，再规定两者如何互锁，避免升级任务直接改变执行器授权。

计算响应时间而非只看利用率

假设单核固定优先级可抢占调度，高优先级任务执行 0.2 ms、周期 1 ms；控制任务执行 0.7 ms、周期 5 ms，最多被低优先级资源阻塞 0.1 ms。采用简化响应迭代 R=C+B+ceil(R/1)×0.2，从 0.8 开始得到 1.0，再迭代仍为 1.0 ms，满足示例 2 ms 截止期。

这要求执行上界、阻塞上界和调度假设可信；还未计释放抖动、多核干扰和中断。若配置写入持锁 3 ms，阻塞变成 3 ms，原结论不再成立。不能把总利用率较低当作时限充分证据，也不能只测平均控制耗时。

在响应时间实验中先预测参数变化，再观察长阻塞如何放大干扰。配置操作应在后台完成验证和持久化，控制周期边界只交换一份已验证的快照，避免在实时路径执行擦除、下载或复杂解析。板级实现还需测量最坏观测与其适用负载，并诚实说明测量值不是数学上界。

配置提交是事务，不能原地覆盖

双槽日志保存两份带格式版本、代次、长度和完整性信息的配置。更新时写非活动槽，写完并验证后才让它成为可选择的新记录；旧槽在新记录完整前保持有效。恢复时只在完整记录中选择最新合法代次，两份都无效则进入明确的默认或恢复流程，不能随意把全零解释为有效配置。

示例旧配置增益为 100，新配置为 120。若写新记录中断，恢复应得到旧的完整 100；若新记录提交完，则得到完整 120。绝不接受“增益已新、限制仍旧”的混合字段。格式迁移也必须版本化，旧程序回退时是否能读新配置要与升级策略一起审查。

主机双槽日志参考用可控故障研究提交边界，并非真实闪存驱动。文件写入、缓存刷回、块设备、擦除粒度和掉电行为都可能不同；CRC 只能检测所覆盖的损坏，不能阻止攻击者篡改。生产系统还需按介质规格处理写屏障、读回、磨损与坏块等约束。

健康来自进度，确认来自完整条件

看门狗喂狗条件应来自关键工作完成，例如采样序号前进、控制输出按期提交和必要状态检查通过。单独高优先级定时器不停喂狗，可能让控制线程永久卡死却不复位。采用任务心跳时还要检查时间窗与代次，旧心跳不能被反复当作新进度。

A/B 升级进入试启动后，新镜像先保持受限模式，校验配置、输入与控制健康，再按第 62 章规则确认。看门狗复位应计入失败试启动，计数耗尽后回到已确认槽。成功下载、内核启动和控制可用是不同里程碑，任何一个都不能被自动等同为最终确认。

若后台日志写入卡死但控制仍健康，策略可选择限制更新并告警；若控制输出停止，则应触发设备定义的安全动作和恢复。把这些差别写成健康矩阵，让“系统还活着”的含义可以被测试。安全启动认证仍需真实信任路径，主机状态变量不提供密码学保证。

运行第二项目并核对恢复状态

控制与恢复参考源码可独立运行：

python -m unittest discover -s labs/tests -v
python -m labs.reference.recovery

基线输出中 timeout_safe、reboot_safe、replay_rejected、persistence_failure_safe 均应为 true，recovered_sequence 为 2。序号 1 在 tick 0 设置输出 60，tick 2 仍有效，差值恰为 3 的 tick 3 进入 SAFE、输出 0。重启始终从 SAFE 开始，只恢复持久化的末序号用于拒绝重放，不自动重放旧设定值。

新序号 2 持久提交后才允许输出 30；序号 3 写入中断则保持 SAFE，恢复末序号仍为 2。继续验证日志适配器抛出 OSError 或代次耗尽的 OverflowError 时，输出已先置 SAFE；异常仍由上层处理，不能假设方法正常返回。该顺序使运行中的旧输出不会因存储异常而继续保持。

A/B 策略把 verified 视为外部可信验证器的输入：验证失败或版本低于 floor=3 时试启动前拒绝，活动槽仍 A；不健康候选尝试 3 次后回 A，floor 保持 3；健康候选确认 B，floor 更新为 4。布尔值不执行真实验签，也没有实现受保护防降级计数器。

再组合配置中断、失败试启动与过长阻塞，记录槽、代次和输出授权。模型注入整数 tick，不证明墙钟实时性；SAFE=0 只是本练习定义，不是通用执行器安全策略。真实介质掉电、密码学认证和闭环稳定性均需独立验证。

交付可审查的恢复闭环

为每个故障列出检测者、检测延迟、即时动作、持久影响、下次启动和恢复授权。示例“配置新槽未完成”：完整性检查发现；控制继续使用旧快照；重启选择旧完整槽；后台可重新提交。若不能说明最后一步，系统只是检测到问题，还没有形成恢复闭环。

恢复也要受资源预算约束：持续重启可能耗尽日志空间，重复写状态可能加速磨损，无限下载会挤占关键流。为重试加次数、间隔和总量限制，并保留可用恢复入口。关键配置无需每个控制周期都落盘，先定义需要持久化的事件和可接受丢失窗口。

验收包含响应预算、配置格式、状态图、故障矩阵和实际执行证据。板级迁移先验证单个介质事务，再验证独立启动回退，最后接入受控被控对象；执行器有能量时遵守已有实验室操作流程。课程项目的完成意味着学习者能解释每项证据与缺口，不意味着获得工业控制或安全启动的产品认证。
