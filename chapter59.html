可复现的崩溃诊断：构建身份、core与跨层证据

从故障现场身份开始，结合符号、消毒器、寄存器与交易序号，把一次崩溃缩成能解释因果的最小复现。

GOALS

本章要交付什么

为一次解析或生命周期失败制作可独立重现的故障包，包含输入、版本、首次错误和修复证据。

  • 建立包含ELF、build ID、输入、环境和复现命令的故障包
  • 用匹配符号读取core并区分崩溃位置与根因
  • 按缺陷类型选择ASan、UBSan和线程检查且说明盲区
  • 用事务序号与时间关联CPU、驱动、DMA和PL证据

机制、约束与验证

每条结论说明条件，每个实验保留可以复查的结果。

先证明你分析的是同一次构建

崩溃分析的第一步不是猜原因，而是固定身份：板卡和硅版本、内核提交及配置、设备树、bitstream、应用ELF、共享库、编译器、构建选项和输入。保存build ID与文件哈希，用于匹配部署物和调试符号。同名app.elf并不意味着相同构建，重编译后即使源码未改，布局也可能变化。build ID用于识别构建，不是软件真实性或防篡改认证。

# Linux/交叉工具链终端；替换成现场真实文件名
readelf -n app.elf
sha256sum app.elf system.dtb system.bit
uname -a
cat /proc/version

在发布流程中同时归档带符号ELF、实际部署文件、map和源码提交。若符号被分离，确保debug link或build ID能找到对应调试文件。core也可能包含敏感运行数据，应按项目的数据处理要求保管。故障单至少能回答“哪个版本、什么输入、什么前置状态、如何触发、预期与实际差异”，否则再熟练的调试器也只能分析一个身份不明的快照。

core冻结现场，不重放时间

Linux用户进程core通常保存崩溃时的线程、寄存器及部分内存映射，能解释最后一个非法访问，却不会记录此前每一次写入。先检查core是否完整、可执行文件和共享库是否匹配；交叉GDB应设置正确sysroot或共享库搜索路径。内核oops、裸机异常和用户core是不同证据载体，不能用一份用户core推断PL内部历史。

# GDB命令示例；文件来自同一次部署
gdb app.elf core
(gdb) info files
(gdb) info sharedlibrary
(gdb) thread apply all bt full
(gdb) info registers
(gdb) x/12i $pc-16

栈回溯可能因优化、内联、栈损坏或缺少展开信息而不完整。栈顶落在memcpy不代表memcpy有错，应核查调用者传入地址、长度、对象生命周期和原始指令。PIE/ASLR下要结合映射基址与符号定位，不能把运行虚拟地址直接当链接地址丢给addr2line。现场寄存器是线索，不是单凭一个奇怪地址就能宣布“内存硬件坏了”。

把症状转成可被证伪的假设

建立诊断表，每条假设都指定能支持或排除它的证据。长度越界可由原始帧、对象容量和第一次非法访问支持；释放后使用可由分配/释放栈及异步回调关联支持；DMA覆写需要设备地址、长度、完成和缓冲区所有权证据。一次通过的RAM测试无法直接排除软件越界，一次缓存关闭后不复现也不足以证明缓存硬件缺陷。

现象优先证据下一步实验
只在长帧崩溃原始长度、容量、边界检查最小化到首个失败长度
remove后回调崩溃释放栈、回调序号、停止顺序延迟回调并检查生命周期
DMA后首尾损坏映射范围、缓存线、描述符独占缓存线并固定图样

表中是诊断策略，不是已发生在本课程的事故报告。每次只改一个关键条件并保留失败和成功对照。改变优化、频率或日志可能只扰动时序，不能作为根因修复。最终解释应包含哪条契约被破坏、为何产生该现象，以及修复后哪个反例被排除。

选择能暴露第一处错误的工具

ASan适合发现许多CPU发起的越界、释放后使用等内存错误；UBSan检查选定的语言未定义行为；TSan检查受支持线程模型中的数据竞争。它们需要相应编译插桩与运行库，不同平台支持不同，不能假定裸机2020.2 BSP直接可用。ASan也不会自动监控设备DMA对物理内存的任意写入。主机测试可移植解析与算法核心，再将修复带回目标系统验证。

/* 保存为uaf.c：故意触发释放后读取的完整诊断反例 */
#include <stdlib.h>
int main(void) {
    int *p = malloc(sizeof *p);
    if (!p) return 1;
    *p = 7;
    free(p);
    return *p; /* 故意错误，仅在实验中运行 */
}
# 装有Clang与ASan运行库的Linux主机
clang -O1 -g -fsanitize=address -fno-omit-frame-pointer uaf.c -o uaf
./uaf

此实验的成功标准是诊断器报告错误并定位分配、释放和非法读取，而不是程序正常退出。修复应消除悬挂访问，不是屏蔽告警。ASan与TSan应分开构建；检查器改变时序和内存布局，仍需保留原发布构建的复现路径。

跨CPU、DMA和PL关联同一笔交易

给每个请求一个事务序号和缓冲区代次，在用户提交、驱动入队、描述符启动、IRQ完成、回调和PL帧头处记录。地址被复用时，只有指针相同无法判断是否同一个对象；代次能区分先后生命。PL ILA、Linux日志和应用时间戳可能使用不同的时钟基准，必须通过共同触发、计数器对照或可测误差窗口关联，不能直接拼接绝对数值。

例如要检查“第42笔完成后读取仍旧”，先确认PL产生的是42、DMA目标属于42代次、IRQ确认的是对应通道、CPU在取得所有权后读取，最后才判断缓存或协议。IRQ到来不一定等于全部数据写入完成，含义必须查控制器协议。高频路径可用固定大小环形事件记录器，失败后导出最近窗口；记录器本身也要有并发和溢出策略，避免为了追查竞态引入第二个竞态。

最小复现保留因果，缩掉噪声

最小化先固定失败输入与随机种子，再减少帧数、模块、线程和参数，直到保留触发契约破坏的最小条件。对于协议崩溃，保留原始二进制而不只贴格式化日志；对于并发缺陷，保存事件顺序与人为延迟点，而不把偶发失败改写成“有时卡死”。每次缩减后重复确认同一种首个错误仍然出现。

利用解析器参考实现及实验测试框架，将失败字节流改成固定回归数据；持久化问题则固定断电切点。运行python -m unittest discover -s labs/tests -v可执行实验包自检。这里的Python例程验证算法边界，不提供ARM core仿真。若只在板端出现，继续保持原ELF和设备环境，借助异常寄存器、硬件断点或总线证据缩小范围，不以“主机跑不出来”结束调查。

用故障包而非动画验收

本章适合静态诊断流程与证据表，没有用于模拟真实崩溃的动态演示。故障包应包含原始输入、复现命令、构建身份、首次错误位置、相关状态/交易日志、最小反例、修复理由与回归结果。未证实的假设单列并标注缺少哪份证据，不用虚构板卡输出填空。没有目标硬件时，可完成ASan反例和主机核心自检，但应明确尚未验证A9现场。

一个完整结论例如“长度字段未先与剩余输入比较，导致第一个越界读取；修复为减法式边界检查，并用最短失败帧及所有截断前缀回归”，它可被独立复核。相比“加延时后恢复”更有解释力。将每次故障中缺失的身份或事件补入下一次构建的可观测性设计，使后续问题无需重新猜地址来源。诊断效率首先来自事前保存正确材料，其次才是现场操作调试器的熟练度。

工程任务 · 为一次解析或生命周期失败制作可独立重现的故障包，包含输入、版本、首次错误和修复证据。

在支持的Linux主机编译运行ASan反例，修复后复验；对真实目标ELF核对build ID并演练匹配core的线程回溯。

故障练习：故意用另一构建的符号分析现场副本，记录不匹配或地址错位证据，再换回正确产物；不得覆盖原故障包。

验收：另一位工程师依据故障包可触发同一首个错误；修复针对契约而非延时；主机和目标验证范围分开记录。
