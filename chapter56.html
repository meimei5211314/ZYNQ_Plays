让RTL自己报错：断言、覆盖与自检验证

以AXI-Stream源为载体，把协议、数据与恢复要求写成可运行检查，建立能发现故意缺陷的验证闭环。

GOALS

LEARN

机制、约束与验证

每条结论说明条件，每个实验保留可以复查的结果。

先写可观察的需求

“波形看着正常”无法判断没出现的场景。以AXI-Stream源为例，传输仅发生在时钟沿上TVALID与TREADY同时为1时；阻塞期间有效载荷必须保持；源不能等TREADY出现才决定是否声明已有数据；TLAST必须与对应的数据拍一起保持。先把这些规则写成明确的采样点和失败条件，再写激励。

验证分四层：协议安全性检查信号行为是否合法，功能检查序号和计算结果，进度检查在已声明环境条件下最终完成，恢复检查复位或错误后重新开始的契约。数据可以全对而握手违规，也可以接口合规却漏了一拍。测试计划应为每条需求指定驱动方式、检查器、覆盖点和失败证据，而不是用“运行了十万周期”代替覆盖目标。只要观察点定义不清，增加仿真时间往往只会产生更大的波形文件。

把背压稳定性写成性质

下面SVA片段在当前周期有效而未被接收时，要求下一采样周期继续有效并保持载荷。即使下一周期TREADY已变高，接收的也必须是原来那拍。若接口存在TKEEP、TUSER等有效载荷侧带信号，也要纳入稳定性检查。复位采用何种极性及何时允许采样，需要与DUT约定一致。

// SVA示意片段，需支持相应断言语法的仿真器；非完整testbench
assert property (@(posedge clk) disable iff (!rst_n)
  (tvalid && !tready) |=>
  (tvalid && $stable({tdata, tlast})));

安全性质只说“不发生坏事”，不能证明系统会前进。若接收端可以永远不给ready，源无法保证完成；活性检查必须写明“ready在K周期内至少出现一次”等环境假设，再对完成时间给界。形式验证中的assume约束环境，assert检查设计；把设计应满足的规则错误写成assume会让工具避开缺陷，甚至导致空洞通过。

scoreboard只在交易发生时更新

驱动器负责产生合法输入，监视器只在握手边沿记录交易，参考模型计算预期，scoreboard按交易比较。若源发送0、1、2、3而ready图样为1、0、0、1，前四个采样沿只接收两拍。用仿真周期数推进期望序号会把背压误判成丢数，或者反过来掩盖DUT在阻塞时错误递增计数器。

// 检查逻辑示意片段；expected仅在接收时推进
if (rst_n && tvalid && tready) begin
  if (tdata !== expected) $fatal(1, "sequence mismatch");
  expected = expected + 1;
  received = received + 1;
end

四态仿真中使用!==有助于把未知值也判为失败。复位时要清空还是保留参考队列取决于设计契约，不能让参考模型自动复制DUT内部状态。若验证变换型模块，参考模型应从已接收输入计算输出，避免与RTL使用相同的错误位宽截断方式。两个模型共享同一种错误公式，即使比较全通过也没有证明功能正确。

覆盖率回答测试有没有问过问题

代码覆盖表示某些语句、分支或翻转出现过，功能覆盖表示需求定义的场景出现过。两者都不证明输出正确。建议对阻塞长度分桶0、1、2–7、8以上，交叉覆盖“帧首/帧中/末拍”和“阻塞/不阻塞”，另列复位发生在空闲、有效阻塞和最后一拍的场景。只统计ready随机为0的次数，无法知道TLAST是否真正遭遇背压。

假设随机ready为1的概率是二分之一，连续8个周期为0的概率是1/256，但这种概率并不保证指定末拍附近会出现长阻塞。对必须覆盖的边界应添加定向激励，再用固定种子的随机测试扩展组合。覆盖空洞需要解释是未激励、设计不可达还是规格遗漏，不能简单把未覆盖行标为ignore。Verilator等工具的断言与覆盖支持随版本变化，应记录版本、开关及不支持的语法。

自检实验应能主动失败

可运行源模块见labs/rtl/axis_source.sv，配套testbench及命令见实验包说明。先跑ready恒高得到连续传输基线，再执行单周期阻塞、长阻塞、末拍阻塞与复位恢复。仿真必须以自检通过或非零失败码结束，超时也要判失败，不能让永远没有输出的设计无限运行而“无报错”。

随后在实验副本中制造一个突变：让数据计数器每周期增加，而不是在握手成功后增加。此时背压稳定性或scoreboard应该报错。如果两者都没失败，说明激励没触及背压，或检查器的采样/推进方式有缺陷。再试移除TLAST保持、把帧长度少算一拍等不同突变，检查它们是否分别被协议和功能检查捕获。这种小规模突变验证比单纯追求覆盖百分比更能证明测试具有发现问题的能力。

复现记录要比波形更早产生

每次运行先输出DUT版本、仿真器版本、参数、随机种子和测试名称；失败时输出仿真时间、已接收笔数、期望/实际数据及最近若干交易。将种子与最小失败序列保存为回归用例，再缩小到一个边界条件。只传一个没有源码版本的VCD，往往无法判断它来自哪次构建，也无法重建刺激。

调试先找第一次分歧，再顺着因果链回看，避免盯着下游连锁错误。testbench若与DUT在同一posedge无明确调度约定地读写信号，可能出现仿真竞争。可用clocking block、明确驱动相位或仿真器支持的调度方案，使驱动在采样前稳定、检查在DUT更新后进行。不要用随意的#1延迟堆叠来掩盖调度问题；时间单位、精度和仿真器语义也应写入实验环境。

浏览器模型与真实RTL各自证明什么

本章复用AXI-Stream交互，适合逐拍观察valid/ready和背压；它是协议教学模型，不是SystemVerilog仿真器。真正的模块验证要运行配套RTL自检，并检查综合、时序和CDC结果。RTL仿真无法证明实现满足时序，二态仿真也可能看不到四态未知传播，形式证明则受环境假设、边界和工具支持约束。

验收按需求而非工具名称组织：握手规则由断言覆盖，序号与TLAST由scoreboard覆盖，长阻塞和复位组合由功能覆盖确认，超时和故意突变证明检查会失败。板上ILA只捕获有限窗口，可用来验证实际系统触发路径和外设交互，但不能替代可重复的回归集。把同样的方法推广到AXI-Lite寄存器时，还要分别处理读写独立通道、响应和复位，不能把Stream的单一握手模型直接复制过去。

工程任务 · 为固定帧长AXI-Stream源建立定向+随机自检，覆盖数据序列、TLAST和背压稳定性。

运行labs/rtl中的源与testbench，依次覆盖恒ready、长阻塞、末拍阻塞、复位恢复，保存版本与种子。

故障练习：让源在阻塞周期错误递增数据，要求稳定性检查或scoreboard失败；若不失败先修验证环境。

验收：正常用例自动通过，突变用例自动失败；每条需求有检查器与覆盖证据；失败输出可用种子和版本重现。
